# ADR-0002 — Rotavox Owns Pool Membership; Lifecycle Is Modelled

- **Status:** Accepted 2026-10-19. §6 decisions settled the same day by the PD, who took the recommendations on all four
- **Date:** 2026-10-19
- **Context:** M4 UI work. Decided with the PD on 2026-10-19: the UI becomes the source of
  truth for format and music-direction data, and lifecycle states are modelled.
- **Builds on:** `ADR-0001-source-of-truth-and-ownership.md` §3.2 (pool assignment
  migrates to Rotavox), §3.5c (adapter tiers), §3.7 (lifecycle has no owner), §4
  (changesets); `CHANGESET-CONTRACT.md` §6 (fields reserved for v2)

---

## 1. Context

ADR-0001 said that pool assignment belongs to Rotavox *as intent*, and laid out a staged
migration toward that. Nothing has moved yet. `song_categories` is still a seed-time
snapshot derived from `songs.rdj_subcategory_id`. Format data (categories, clocks, grid,
rules) is generated by `tools/m4-seed.mjs` and loaded by a teardown-and-reinsert SQL
seed. The costs show up repeatedly:

- **Membership goes stale silently.** After a changeset, `sync-library` updates
  `rdj_subcategory_id` but not membership. Someone has to remember to re-derive it
  before generating (LIBRARY-CONTRACT.md).
- **A re-seed is destructive.** Re-running the seed NULLs `clock_position_id` on
  approved logs, which breaks TOH timing for the log on air.
- **Tier 0/1 stations cannot have pools at all.** Membership is defined *as* the
  playout system's subcategory. A station that grants no library write, or runs a
  playout system with no bucket concept, has no way to say "this song is an A1".
- **Lifecycle lives in names.** `Z[x]` means "rested, came from *x*". It is a record,
  not a mechanism: ZN reached 148 songs against N's 8 because nothing ever moves a song
  out of rest.

A PD/MD-facing UI cannot be built on any of this. Every edit screen needs a table it
can write to without a later seed or sync overwriting the change.

## 2. Decision

**Rotavox's Postgres is the source of truth for format and music-direction data:**
categories, pool membership, lifecycle state, clocks, positions, the grid, rules and
dayparts. The UI edits it directly. The playout system remains the source of truth for
inventory: existence, path, duration, enabled, cue points and play history (ADR-0001 §2).

Concretely:

1. **Membership is authored, not derived.** `song_categories` stops being rebuilt from
   `rdj_subcategory_id`. The UI edits it, and library sync never writes it. After a
   one-time import (§4) the link to RadioDJ subcategories becomes a *projection* that
   runs in one direction only, Rotavox → RadioDJ, at tier 3.
2. **Lifecycle is a modelled state on each song**, separate from its pool (§3). A state
   is not a pool. Rested songs are not schedulable because of their state, not because
   their pool is left out of the clocks.
3. **Every write goes through a changeset.** Changesets stay the unit of *application*
   (ADR-0001 §4), now authored by the UI. A UI edit drafts a changeset. Review shows
   its impact: depth, turnover and the Balance view. Applying it updates Postgres
   immediately. At tier 3, the Runner then projects the same changeset to RadioDJ and
   emits the inverse, as it does today. Below tier 3, the changeset stays a Rotavox-only
   record. Either way it is versioned, reasoned (`reason` stays mandatory) and reversible.
4. **Format edits are in-place, never teardown.** Clocks, positions and grid cells are
   updated where they are, so approved logs keep their provenance. The seed becomes an
   *import* for bootstrapping a new station, and refuses to run against a station that
   already has format data.

## 3. Lifecycle model

The pipeline from ADR-0001 §3.7: **add → A1 → A2/B → N → rest → recurrent → gold →
bench**. Most of those are pools. Only some are *states*. The test is
FORMAT-WORKFLOW §1a: if the distinction is about direction or time, it is a state.

| State | Schedulable | Meaning |
|---|---|---|
| `active` | yes | In rotation in its pool |
| `resting` | no | Taken off air on purpose. **Keeps its pool membership**, and that pool is its origin. This replaces the `Z[x]` naming |
| `benched` | no | Held in the library with no plan to return (today's W). No pool |
| `retired` | no | Permanently out of the format (today's K, "Killed"). No pool |

A resting song's pool *is* its origin, so no separate origin field is needed. "A1: 7
active, 3 resting" is how a PD reads it anyway. A song rested with no known origin (the
old generic Z) is resting with no pool. Its exit is decided when the rest ends, which
is the default per §6.1.

Direction within currents (rising vs falling) is **derived, not stored**. It is computed
from the pool's position in the ladder and the time since the last transition. That
way nobody has to maintain it by hand (FORMAT-WORKFLOW §1a, item 5; settled in §6.3).

Schema, additive (migration 0005):

- `songs.lifecycle_state` text, not null, default `'active'`
- `songs.lifecycle_since` timestamp: when the state was entered, so rest duration can be measured
- `song_categories.role` text, not null, default `'primary'`: `'primary'` or `'also'`,
  with a partial unique index allowing at most one primary per song (§6.4)
- `categories.rest_review_days` integer, nullable: the standard rest for songs resting
  from this pool (§6.2)
- `categories.rdj_subcategory_ids` integer[]: the projection map, Rotavox category →
  RadioDJ subcategories. Moves the LIBRARY-CONTRACT binding out of `tools/m4-seed.mjs`
  and into the one place every reader can see it (ADR-0001 §3.3).
- `stations.rdj_lifecycle_subcats` jsonb: which RadioDJ subcategories *encode a state*
  rather than a pool, e.g. `{"33": {"state": "resting", "origin": "N"}, "35": {"state":
  "benched"}}`. Station-scoped adapter config.
- `stations.membership_imported_at` timestamp: set by the one-time import (§4). From
  then on, Rotavox owns membership for the station.
- `lifecycle_events` (`station_id`, `song_id`, `from_state`, `to_state`,
  `from_category_id`, `to_category_id`, `source`, `source_ref`, `reason`, `at`): the
  history of transitions. It is what makes "why is this in R2" answerable, and what
  standing rules will read.

UI-authored changesets (migration 0006, built 2026-10-24): `changesets` and
`changeset_items`, one row per song with its from-placement as the precondition. Each
station has at most one draft. Every edit screen stages into it, and Music › Changes
reviews it against the Balance view and applies it as a whole with a required intent.
Undo drafts the inverse, which is reviewed like any other change. An applied changeset is
marked `projection = 'pending'` where the station has a projection map. The Runner's
`project-changesets` command then turns it into a v1 file changeset under
`changesets/rotavox/` and writes it through apply-changeset's validated path. It is
operator-run, not automatic, because it writes the live library. Hand-authored file
changesets still work, and the Runner mirrors their moves into Rotavox (§4, step 3).

Engine change: `basePool` additionally requires `lifecycle_state = 'active'`. It is
one filter, next to `enabled`.

**Standing lifecycle rules** come later. They read song state and `lifecycle_events`
(time rested, spins accumulated, chart position) and *draft* changesets for review.
They never apply on their own. The model above is all they need.

## 4. Migration (one-time, per station)

1. Re-sync the library, so `rdj_subcategory_id` is current.
2. Import (`tools/import-membership.mts`): derive each song's primary pool and state
   from `categories.rdj_subcategory_ids` and `stations.rdj_lifecycle_subcats`:
   ZN → `resting` in N, W/Y → `benched`, K → `retired`, unmapped → active with no pool.
   Write one `lifecycle_events` row per song. Re-running it imports only songs that have
   no lifecycle history yet, i.e. songs added to RadioDJ since. That makes it the
   interim intake path until the Library screen has an "unassigned" inbox.
3. From then on, sync never touches membership or lifecycle. Two paths write them: the
   UI, and changesets applied by the Runner. After a successful RadioDJ commit, the
   Runner mirrors each move into Rotavox using the same mapping, so the two never
   diverge. `refresh-memberships.sql` refuses to run on an imported station. The M4
   seed preserves authored membership across its rebuild, matched by category name,
   and aborts if any would be lost.
4. Drift check: at tier 1+, sync reports songs whose RadioDJ subcategory disagrees with
   their projected Rotavox pool. Someone changed it in RadioDJ directly. The report
   offers two actions: adopt the RadioDJ change as a changeset, or re-project. It
   never silently overwrites either side.

## 5. Consequences

- The memory gotcha "re-derive membership after every changeset" goes away, and so does
  the destructive re-seed.
- Tier 0/1 stations get full pool and lifecycle management. This is required for the
  core product to stand on its own (ADR-0001 §3.5b).
- RadioDJ's AutoDJ fallback stays coherent only through projection. A missed or failed
  projection now leaves RadioDJ stale rather than Rotavox. That is the right way round,
  but it needs surfacing: the Today screen shows any unprojected changesets.
- `tools/m4-format.mjs`, `m4-seed.mjs` and `depth-solver.mjs` become import and
  analysis tools. Their logic moves into the UI over time: the Balance view already
  covers the depth-solver turnover arithmetic.

## 6. Decisions (settled 2026-10-19)

1. **Rest exit path: case by case.** When a song leaves rest, the PD chooses where it
   goes. The UI suggests R1 as the default, with "return to its pool" one click away.
   No automatic exit.
2. **Rest duration: a standard per pool, prompt only.** `categories.rest_review_days`
   sets how long songs resting from that pool rest. Once a song passes it, the song is
   surfaced for a decision on Today and in Lifecycle. It never moves on its own.
3. **B-falling is a state, not a pool.** Rising vs falling is derived (§3). The clocks
   call a single B, so nothing in the data changes.
4. **One primary pool per song,** enforced by the schema, plus explicit `also` eligibility
   for the rare exceptions. Depth counts primaries. `also` rows are shown separately, so
   one song never inflates two pools' depth without anyone seeing it.
